# fs 驱动版本兼容：指令级补丁 vs 整函数替换（选型分析）

> **状态：历史决策记录（2026-09-17），结论已落地 —— 不要按本文动手改代码。**
> 本文里的"29 个锚点 / 全部硬编码偏移"是当时的现状快照。之后：**P1** 把全部改点
> pattern 化（二级表 + 谓词位图，运行时无任何硬编码 fs 偏移），**M6/M8** 把
> `WideChar_Compare` / `FAT_GetNextChar` 改为整函数替换，**14.1.2/15.0.1** 用追加变体族覆盖，
> **P3** 又做了三项扫描结构优化。当前形态与实现细节以
> `patch-design.md`（方案与实现定稿）+ `AGENTS.md`（FS codepage patch 一节）
> + `../design-decisions.md`（设计现状与决策台账）为准。
> 本文也仍有一处已过时的描述：第 2 节的
> 字节级"寄存器必须与原指令一致（`RN_OVERRIDE` 例外）"校验，已随字节数组表一起删除。

> 背景：当前 fs 编码补丁共 **29 个锚点**——5 个整函数替换 + 24 处指令级改写
> （R1 三处步进、R1b 三处访宽、R1c 十处 24 位比较值，以及 NOP/短名等），
> 全部是**硬编码偏移且无固件版本门控**（`AGENTS.md` 已注明"仅对派生偏移的那份 FS 有效"）。
> 目标固件一换，偏移与寄存器都可能变。本文比较两种落地方式，并给出分层推荐。

> 另注：现在的实现是"逐组应用，失败即 break"，因此**失败时前面各组已经写进 fs**
> （部分打补丁状态）——这是比"选哪种补丁方式"更该先修的安全问题（见 §3.1）。

---

## 1. 两种方式的本质差异

| | 指令级补丁（4 字节改写） | 整函数替换 |
|---|---|---|
| 依赖的"契约" | **该条指令的编码与上下文**（用哪个寄存器、立即数多少、相邻指令如何配合） | **函数的 ABI 与语义**（入口地址、原型、行为、结构体布局） |
| 锚点数量 | 每处一个偏移（当前 11 处） | 每个函数一个入口（当前 5 个） |
| 空间需求 | 4 字节（几乎无约束） | 需 ≤ 原函数体（"洞"） |
| 失败后果 | 写错编码 → 崩/挂死（本项目已两次踩坑） | 语义写错 → 功能整体失效（但不会野指针） |

**关键结论**：两者都依赖"偏移"，但指令级还额外依赖**编译器代码生成细节**（寄存器分配、指令选择、
块顺序）——而这正是固件/编译器版本间最容易变的部分。函数替换只依赖"入口 + 语义"，内部怎么编译与我无关。

---

## 2. 逐项对比（针对本项目）

| 维度 | 指令级 | 整函数替换 | 说明 |
|---|---|---|---|
| 抗代码生成变化（寄存器重分配、指令重排） | ✗ 差 | ✓ 好 | 指令级最常见的失效原因 |
| 抗偏移变化（固件版本） | ✗ 差（同样要重推） | ✗ 差（同样要重推） | **两者都要解决"找锚点"的问题** |
| 空间约束 | ✓ 4 字节 | △ 需 ≤ 洞；**若按"跨版本最小洞"设计则无需每版本单独维护** | 见 §3.2 |
| 语义回归风险 | ✓ 低（改动局部） | ✗ 高（要复刻整个函数） | 用主机侧单测对冲 |
| 崩机风险 | ✗ 高（编码写错即野指针/死循环） | ✓ 低（不会写出越界指令） | 已有 3 次事故可佐证 |
| 实现工作量 | ✓ 小 | ✗ 大（需 RE 整个函数） | 一次性成本 |
| 自动化校验 | ✓ 好做（编码规则 + 同址访宽等） | △ 需要行为级测试（主机单测） | 见 §4 |
| 修一类问题的彻底性 | △ 只能逐点修 | ✓ 一次修整类（如匹配器替换即消除碰撞与步进问题） | |

## 3. 推荐方案（分层，按优先级）

### 3.1 先解决"找锚点"：用**模式扫描**替代硬编码偏移（最大收益，与 A/B 之争正交）

问题不在"改一条指令还是换一个函数"，而在"怎么可靠地找到它"。

- 上游 `patches[]` 早已是**字节模式 + 通配符（`.`）+ 相对偏移**的扫描机制，只是 fs 编码补丁没用上；
- 建议把每个锚点（无论是函数入口还是单条指令）改成"**在 fs 代码段内搜索唯一模式**"：
  - 整函数替换：模式 = 现有 16 字节 cmp（函数开头若干指令）→ 命中处即入口；
  - 指令级：模式 = 该指令 ± 邻近若干字节（含通配符吸收寄存器编号变化？不——寄存器变了语义就变了，
    应当**要求完全匹配**，不匹配就跳过并记日志）；
- **唯一性必须在构建期验证**：守卫扫描各受支持 fs 二进制，断言每个模式**恰好命中一次**；
  否则构建失败（避免"搜到别处的相同指令序列"）。
- 运行时：全部锚点命中才应用该组；任一缺失 → 整组跳过 + 记日志（当前 `break` 语义已接近，需改成
  "预检全部锚点再动手"，避免打到一半失败）。

### 3.2 整函数替换：用"跨版本最小洞"做尺寸上限，去掉每版本洞表

- 若替换函数尺寸 ≤ **所有受支持版本中最小的洞**，则无需为每个版本维护洞大小；
- 构建期守卫按"最小洞"校验（把 `FUNCTIONS[*].hole` 语义改成"跨版本最小值"并注明来源版本）；
- 洞仍要在 RE 时确认（下一个函数起点、回调表 stub 等），但只做一次，且保守取值。

### 3.3 选型规则（什么时候用哪种）

| 场景 | 选型 | 例子 |
|---|---|---|
| 该函数的语义我们**本来就要重新定义**（编码转换、判定规则） | **整函数替换** | 两个 per-char 转换器、`isOEMMBchar`、`Str_Unicode2OEM`、`StringDesc_ToUpper` |
| 只是**关掉/放开一个局部判定** | 指令级（NOP / 改立即数） | `0xd4af4` NOP、`0xf5dcc` `mov w23,#2` |
| 只是**局部语义的小幅等价改写**且指令角色无歧义 | 指令级（保持同寄存器、可校验） | 步进改 `add Rd,Rn,w0`、访宽 `ldrb→ldrh`、去掩码 `and→mov`、去扩展 `cmp uxth→cmp` |
| 需要**成类修一批问题**、且函数复杂 | 长期应转向整函数替换（先补单测） | `FAT_MatchWildcardRecursive`（858 字节递归匹配器） |

即：**能用"替换 + 单测"覆盖的尽量替换；只留小、局部、角色明确的指令级微调。**

### 3.4 保留指令级时的硬约束

1. 只允许**等价改写**（改移位量/立即数/访宽/去掩码/去扩展），禁止"照抄字节拼新指令"——历史 4 处
   错误全部来自后者；
2. 寄存器必须与原指令一致（例外需像 `RN_OVERRIDE` 那样具名登记并写清理由）；
3. 每条都要有 cmp 保护 + 构建期编码校验（已实现）。

---

## 4. 让"整函数替换"变安全的前提：主机侧行为测试

替换的最大风险是语义偏差。建议建立轻量测试框架（主机 `gcc`/交叉编译均可）：

- 对**纯函数**（转换器、`isOEMMBchar`、ToUpper、Str_Unicode2OEM）：直接喂字符/字符串用例，比对期望输出；
  （`patch_is_oem_mb_char` 已做过一次 ad-hoc 表驱动验证，值得固化）
- 对**结构性函数**（如匹配器）：先固化"原始语义"用例集（从 fs 二进制行为/RE 结论反推期望值），
  替换实现必须逐条通过；
- 位置无关性、无外部引用等由构建守卫静态保证（已实现）。

有了这层，整函数替换的"语义回归风险"这一最大劣势可被显著压低。

---

## 5. 版本识别与门控

- 粗粒度：`FW_VERSION`（已有 `min_fw_ver`/`max_fw_ver` 机制）→ 至少保证"未知版本不打补丁"；
- 细粒度：锚点模式匹配本身即版本指纹（比版本号更可靠：同一版本号下 fs 也可能有小修订）；
- 运行时策略：**先预检全部锚点 → 全部命中才动手 → 任一失败整组跳过并记日志**。
  宁可"功能缺失"，不可"写错地方把 fs 打挂"（本项目 3 次事故都是后者）。

---

## 6. 迁移路线（建议顺序）

1. 构建守卫：模式**唯一性**校验（扫受支持 fs 二进制集合）→ 先把现有 16 个点固化为"模式 + 相对偏移"；
2. `fs_codepage_patch()` 改为"预检全部锚点 → 整组应用/整组跳过"，并接入 `version_skip` 式的门控；
3. 主机侧单测框架 + 现有 5 个替换函数的用例；
4. 尺寸上限改成"跨版本最小洞"；
5. 评估把 `FAT_MatchWildcardRecursive` 从 10 处指令级（R1b/R1c）升级为整函数替换
   （前提是第 3 步的用例集已覆盖通配/折叠/递归语义）。

---

## 7. 一句话结论

> **找锚点用"唯一模式扫描 + 版本门控"（这是兼容性的根本）；
> 需要重新定义语义的一律整函数替换（靠主机单测兜底）；
> 只留小、局部、可机械校验的等价改写用指令级补丁（并严禁手写新指令编码）。**

## 8. 换固件时的自动化（2026-09-17 新增）

上面「先读文档再手工重推偏移」的流程已脚本化：**`scripts/fs_fw_audit.py`**。

- `all <固件 zip|目录>` = 自动走完 `ns_reverse/cmd.txt` 的解包链路（头扫描定位
  BootImagePackage → cnmt → package2 → INI1 → `kip1 --uncompressed`），然后解析
  `main.cpp` 的全部补丁点、逐点重定位、写 `report.md`。
- 定位分层：同址 → 精确唯一 → 锚点投票 → 块漂移印证；打分用**语义匹配率**
  （忽略 `B/B.cond/CBZ/CBNZ/TBZ/TBNZ/ADR/ADRP/literal LDR` 的位移）。
- 关键指标是 **`cmp 精确命中 N/29`**：`fs_patch_function()` 会逐字节比对 `cmp`，
  不命中就整点跳过，所以"定位看着对"不等于"能落地"。
- `holes` 重推每个替换函数的洞（锚点定位基线里的边界函数入口，兜底用"旧洞投影 +
  边界特征校验"），并读 `fs-codepage.elf` 符号表算余量。

**19.0.1 实测：29/29 定位成功、0 需人工确认、cmp 精确命中 29/29，5 个洞与基线一致。**
（该次审计的原始偏移表/洞表已删；需要时用 `scripts/fs_fw_audit.py` 重跑。）

第 6 节里"文档里全是原始字节/偏移、守卫只做机械校验"的现状没有变——
这个工具补的是**换版本时把新偏移找出来**这一步，仍然需要人工确认后才写回 `main.cpp`。
