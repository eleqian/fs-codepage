### 三个关键教训
1. **寄存器重命名必须按「操作数位置」分开目的/源**。18.x `csel x9,x20,x23,eq` 只是结果改写到
   临时寄存器 x9，源 x20 没变；用全局映射 x20→x9 会把 patch `add x20,x20,x0` 错改成
   `add x9,x9,x0`。分位置后得到 `add x9,x20,x0`（正确）。
2. **「字节完全相同」的判据应是 `newcmp == 基线cmp`，不是「没推导出寄存器映射」**。
   后者会漏掉「寄存器没变但立即数/寻址变了」（如 `ldrb [x26,x27]` → `[x26,#1]`）。
3. **更通用的推导 = 以目标固件指令为骨架，只搬运 patch 相对 cmp 的操作数差异**：
   助记符 cmp→patch 变了就用 patch 的（ldrb→ldrh、strb→sturh），否则用目标的；
   操作数同理。编译器重排指令时按「助记符 + 最近距离」在目标里找对应指令，不要按下标对位。

### 各版本「换写法」速查
- 22.x #1：`sub w,#,0x7f; cmn w,#,0x5f; b.lo` → `cmn w,#,0x60; b.ls`（取分支那条，0xE6F80/0xE7040）
- #10 CompareOem 三代：19.0.1 `csel x20,x20,x23,eq`；18.x `csel x9,x20,x23,eq`+add；
  17.x/16.1.0 `cinc x9,x20,ne`+add。patch 统一 = `add <新目的>, <新第1源>, x0`。
  定位：CompareUnicode(#9) 与 StringDesc_ToUpper(#29) 之间，`cmp w0,#0` 后两条内的条件选择族。
- 16.1.0：`orr wD,wN,wM,lsl #8` → `bfi wN,wM,#8,#8`（+ 后面一条 mov）。
  补丁 lsl#8→#16 对应 `bfi wN,wM,#16,#8`（a8 1e 10 33 / c8 1e 10 33）。

# 2026-09-18（下午）落地：fs 补丁从「29 点硬编码偏移」改成 pattern 驱动（模糊匹配）

## 目标（用户原话）
「参照原本 sys-patch 补丁方式，寄存器变化可以使用模糊匹配，避免硬编码地址偏移，减少版本绑定」

## 结果
- `sysmod/src/main.cpp` 的 fs 段整体重写：**不再有任何 `mem_info.addr + 0xXXXX` 硬编码**。
  改为 `fs_stages[]` / `fs_cp_patterns[]` / `fs_codepage_blobs[]` 三张表 + 原有 `patcher()` 扫描。
- 三张表由 `D:/Game/NS/firmware/_audit/_gen_cpp.py` 从已逐变体验证的 `PATTERNS.json`
  **机械生成**（`_cpp_tables.txt`），再由 `_splice_main.py` 拼进 main.cpp。**无手抄字节**。
- 规模：**34 条 pattern + 6 条 blob**，覆盖 RESOLVED.md 的 **29 个补丁点**、48 变体。

## 核心机制（记录要点）
- **pattern = 字节模板**，通配位写成 `.`（= `REGEX_SKIP=0x100`）；命中后在 `i+inst_offset`
  取 `inst`，`cond(inst)` 为真才在 `addr+inst_offset+patch_offset` 写 `patch(inst)`。
  寄存器/地址/宽度**全部从命中现场继承** → 天然寄存器无关，这就是"模糊匹配"。
- **`patch(inst)` 只做「立即数形式 -> 移位寄存器形式」的等价改写**（如 `add w,#imm` ->
  `add wD,wN,w0`；`ldrb`->`ldrh`；`orr lsl#8`->`lsl#16`；`bfi #8,#8`->`#16,#8`；
  `csel/cinc`->`add`；`and #0xffff`->`mov`；`movz #0x2e`->`movz #2`）。
  规则都在 `constexpr rules_*()` 里，镜像 `_audit/_fsrules.py` 的位域。
- **函数体替换类（#2/#3/#4/#28/#29，6 条 blob）** 仍走整函数写入：表里存
  `FsBlobImpl` **枚举**（不是函数指针！）——`constinit` 不允许 `reinterpret_cast`/取函数地址，
  运行期用 `fs_blob_range(impl)` 的 switch 换回地址。这条是硬约束，别再试图往表里塞指针。
- **stage 门控保留**：`fs_stages[]` 的 `limit_idx`（非递减）+ `needs_wide_cmp`；
  仍读 `[fs_codepage] stage=N` / `wide_cmp=0`；逃生开关 `[options] fs_codepage=0` 不变。

## 版本族差异 -> 同一补丁点有多条 pattern（本次新引入的概念）
- 一份固件只会命中同一补丁点的**其中一族**，另一族 0 命中是**正常的**，不是错误。
  例：#17~#20 的 `bfi` 形式只在 16.1.0，`orr lsl#8` 形式在 20.x+；
  #10 有 8 组/14 组两族；#28 两族 `entry_offset` 不同。
- 因此构建守卫的判据是**按补丁点汇总**：名字里的 `pNN` 是点号，

  - 点内 0 族命中 -> **ERROR**（该点在目标固件上没定位到）；

# 2026-09-18（傍晚）★ 严重缺陷修复：patch_str_unicode2oem 的 fs 上下文槽地址不能写死

## 用户提出的问题（一针见血）
「patch_str_unicode2oem 中使用的 got 表在不同固件版本可能有差异，确实是否能兼容」

## 结论：不兼容，而且是会崩的那种不兼容
- 该替换函数要读 fs 的**代码页上下文指针**，原实现把取指对**硬编码**成
  `adrp x3,+0x159000`（=0xb0000ac3）+ `ldr x3,[x3,#0xb50]`（=0xf945a863）→ fs+0x24EB50。
- 实测 22 个 fs 二进制，**槽地址逐版本不同**（14 个不同值）：
  `19.0.1/exfat=0x24EB50`、`19.0.1/fat32=0x240B50`、`16.1.0=0x2797D0/0x26C7D0`、
  `17.0.0=0x23BE90/0x22EE90`、`18.x=0x23D138/0x230138`、`20.x=0x263F40/0x256F40`、
  `21.x=0x25CBC8/0x24FBC8`、`22.x=0x25FC38/0x252C38`。
  **连 adrp 页增量（0x159/0x195/0x154/0x163/0x145…）和 ldr 立即数（0xB50/0x7D0/0x138/0xF40/0xBC8/0xC38/0xE90）
  都不同** —— 也就是说没有任何固定关系可依赖。
- 后果：除 19.0.1/exfat 外的每一份固件上，补丁会算出**野指针**再解引用（读 `ctx[0x48]`）→ 大概率崩。
  这也解释了为什么"pattern 化去掉了偏移硬编码"之后仍要单独查这一条：偏移模式是模糊匹配了，
  但这个**数据槽引用**是另一类硬编码，ASLR 守卫（只管绝对地址物化）管不到。
- 讽刺的是**函数体本身**是 pattern 定位的（落点随版本变），所以守卫里
  `(site+off)&~0xFFF == 0xF5000` 那条同页检查只对参考固件成立，等于没查。

## 修法：从「即将被覆写的原函数字节」里现场收割
信息就在脚下 —— 原版自己就是用 `adrp xN,<页> + ldr xN,[xN,#imm]` 取这个槽的。所以：
1. `patch_str_unicode2oem` 的最前两条指令改成**哨兵占位**：
   `.inst 0xDEAD0001` / `.inst 0xDEAD0002`（常量 `FS_CTX_SENTINEL_A/B`），后面照旧 `mov %0, x3`。
2. `fs_blob_patcher()` 在写之前（对 `FsBlobImpl::StrUnicode2Oem` 这一个点）：
   - 用 `svcReadDebugProcessMemory` 读入口起 `0x120` 字节（= 原函数体，不依赖 chunk 边界）；
   - `fs_harvest_ctx_pair()`：扫出**唯一**一条 adrp 与其**唯一**配对的 `ldr`（要求 Rn=Rt=adrp 的 Rd），
     解码目标页与立即数，校验槽在函数体之后且距代码 ≤0x400000（实测 1.3~1.7 MB）；
   - 用**占位对自身的真实地址**重新编码 adrp（Rd/Rn/Rt 归一到 x3），连同 ldr 一起覆写哨兵；
   - 因为按真地址重编码，**不要求替换体和原指令同页**（跨页也正确），
     这一步把"必须落在 0xf5000 页"这个隐含约束也一并去掉了。
3. **收割失败 → 整点跳过不写**（新枚举 `PatchResult::FAILED_HARVEST`，log 显示
   `Failed (fs ctx harvest)`）：宁可保留原版函数（中文名退化为原行为），也绝不写会解引用野指针的代码。
4. 「已打过」判定要拿**替换后**的 body 比对（哨兵逐版本重编码不同，拿静态体比会永远判成没打过）。
   收割对已打过站点**是幂等的**（替换后头两条仍是 adrp+ldr，且体内无第二个 adrp）。

## 验证（全部通过）

- `_audit/_check_ctx_harvest.py`：收割启发式的逐版本明细（adrp 恒在 +0x1C/+0x20、恒用 x21、唯一配对）。

# 2026-09-18（傍晚）fs 补丁点「合并优化」分析

## 问题（用户原话）
「指令集补丁点非常零散，数量多，分析如何优化合并」

## 结论一句话
「零散」不是补丁**数量**问题，是**组织维度**问题：40 条条目按「站点」扁平排列，
导致同一函数的 15 个点被拆成 19 条，又因编译期写法差异再分裂出 11 条版本族。
- **改写条数不可压缩**（每站点一次独立改写，语义决定）。
- **可压缩的是**：①定位方式 ②扫描遍数 ③写入次数 ④条目组织。

## 实测盘点
- 40 条目 = 34 字节模板 + 6 整函数替换；29 逻辑点；**11 条是版本族/多改法冗余**。
- 指令类 24 点落在 **9 个函数**；其中 **15 点挤在同一个 872 B 函数**（占 .text 0.05%）。
- 26/34 模板含通配，共 **79 个通配位**。
- `.text` 1.79–1.99 MB；每次启动扫描 = 40 模板 × 1.83 MB ≈ **73 M 次位置探测**。

## 决定性实验（全部 22 个 fs 二进制）
- **E1 「函数+固定相对偏移」→ 否决**：相对函数起点的偏移跨代次漂移 ±8，29 点里只有 2 点恒定。
- **E2 「规则全段定位」→ 否决**：`ldrb_reg` 全段命中 5600–7000 次，`add_imm` 3.7 万次；规则太泛。
- **E3 「函数内规则直方图」→ 成立 22/22**（本次核心发现）：
  - 15 点函数的 9 维直方图**跨版本恒定**：add_imm=16、add_w25_2=2、and_ffff=8、cmp_uxth=2、csel=10；
    ldrb_reg 6/4、ldrb_imm 0/2、orr_lsl8 3/0、bfi 0/3（20 个 orr 族 vs 2 个 bfi 族）。
  - 该直方图在**整个 .text 的全部函数区间里唯一**（候选 8775–9736 个，命中 1 个）→ 22/22。
  - **序号恒定**：p11=add_imm#5、p13=#15、p12=add_w25_2#2、p14/p15/p16=ldrb#2/4/6、
    p18/p19/p20=orr∪bfi#1/2/3、p21/p23/p22/p24=and_ffff#2/3/4/5、p25/p26=cmp_uxth#1/2。
  - **★ 用「统一谓词」（`orr` 或 `bfi` 都算命中、`ldrb_reg` 或 `ldrb_imm` 都算命中）后，
    序号在 22/22 上仍然恒定 ⇒ 11 条版本族冗余可全部删除，且不需要新写任何字节模板。**
  - `is_add_w25_2` 是全 .text 只命中 2–3 次的稀有谓词，可当**廉价全局预筛**：
    定位成本 73 M → ~0.5 M（~150×）。注意它带具体寄存器号 `w25`，只能当预筛不能当判据。

# M6 可行性实测（结论：不做；前提被证伪）

用户问：「尝试 M6，将多个指令补丁合并成函数整体替换，在所有固件版本函数实现是否等效」。
M6 = 把承载 p11–p26 的 15 个补丁点合并成**整函数替换**。前提 = 该函数在 22 个 fs 二进制里
是不是同一份实现。**答：不是。**

脚本 `_audit/_m6_equiv.py`（新），完整输出 `_audit/_m6_report.txt`。

## 方法要点（可复用）
- **定界**：`上一个 ret 之后 → 下一个 ret`（`_merge_probe2.span`），**必须再裁掉首尾全零
  `udf #0` 对齐填充**，否则会把前一个函数的尾巴算进来（第一版就踩了：20.x 多出 3 条 `udf #0`）。
- **三级归一化**（关键：区分「代码不同」与「引用搬家」）：
  `raw` 原始字节 / `PC±d` PC 相对换算成相对位移（保留位移量）/ `PC@` PC 相对抹平（只看代码本身）。
  **只有 `PC@` 级才是在回答「代码是否相同」**。
- **L3**：先把本组 15 个点的改写规则应用上去，再比 `PC@`。

## 结果：22 → 7 归一化组 → **3 个形状**

| 级别 | 分组数 |
|---|---|
| L1 原始字节 / L2a PC±d | 14 |
| L2b `PC@` | **7** |
| L3 打补丁 + `PC@` | **7**（打补丁**不**收敛版本） |

| 形状 | 归一化组 | 二进制数 | 指令数 | 相对 A |
|---|---|---|---|---|
| **A** | 17.0.0 / 18.x / 19.0.1 / 20.x | **12** | 215 | —（两两只差 **1 条**） |
| **B** | 21.x / 22.x | **8** | 219 | 48 条 |
| **C** | 16.1.0 | **2** | 223 | 32 条（与 B 差 70） |

- **A 内部逐字节相同**：唯一差异是 1 条 `ldr xN,[xN,#disp]` 的**数据槽位移**（不是代码）。
- **B vs A 不是寄存器重命名**（已证伪）：`w22→w21`/`w24→w23`/`x23→x22` 貌似重命名，但把推导出的
  映射施加到 A 上时，在 **8 条「两边原本完全相同」的指令**上自相矛盾（反例
  `stp x24, x23, [sp,#0x60]`：A 里 x23 既是保存寄存器又是数据指针，B 拆成 x23/x22）

  `ldrh w9,[x9,x8]` → `ldrh w9,[x9,w8,uxtw]` 与 4 条调度差异。
- **C vs A**：栈帧 `sub sp,#0x90`→`#0x80`、保存寄存器布局不同、
  `orr lsl#16` vs `bfi #0x10,#8`+`mov`（即已知 orr/bfi 版本族）、多若干 nop。
  交叉验证：**C = E3 里的「bfi 族 2 个二进制」**，A+B = 20 = orr 族 ⇒ 与 E3 的 20/2 完全吻合。

| 22.x | 0x25FC38 | ✓ |
| 16.1.0 | 0x2797D0 | ✓ |

`disp` 取值 0x138 / 0xe90 / 0xb50 / 0x7d0 / 0xf40 / 0xbc8 / 0xc38（A 形状那"1 条差异"就是它）。
⇒ ①这份函数的宽字符比较逻辑受同一个上下文槽控制（与 `[fs_codepage] wide_cmp` 同源）；
②M6 需要的 adrp+ldr 回填**已有现成收割实现**（`fs_harvest_ctx_pair`）。

## M6 的硬成本（形状 A 为例，每份二进制）
| 类型 | 数量 | 是否必须回填 |
|---|---|---|
| `bl` | 4 | **是**（1 处**自递归** `bl <函数入口>`；3 处指向紧邻前一函数 0xf2940） |
| `blr x8` | 3 | 否（寄存器间接） |
| `adrp` | 1 | **是**（数据槽页） |
| `adr` / 字面量 `ldr` | 0 / 0 | — |
| 函数**内**跳转 | 38 | 否（原地替换位置不变） |
| 函数**外**跳转 | 3 | **是** |
| **合计需回填** | **8 处/版本** | |
**关键区分**：「原地整函数改写」（保留原 PC 相对指令字节）**不需要回填**；
「搬到别处 / 自写新实现」才要付这 8 处。M6 走的是后者。

## 结论
**M6「一份实现覆盖 22 版」不可行**（3 个形状）。退一步「每形状一份」也不划算：
省 16 条条目，代价 = 完整逆清 215/219/223 条指令 ×3 + 24 处回填 + **把 fail-safe 的单点失效
换成整函数失效**。⇒ **维持「不做 M6」**，与报告 §4 初判一致，现有量化依据（报告新增 §9）。

## 副产物（喂给 P2）
形状 A 的函数体是**准常量指纹**（12 个二进制逐字节相同）。作为**定位器**太脆（挪一条指令就整段失配），
但作为**校验器**很好：P2 定位到函数后，用这段 860 B 指令序列（PC 相对位 + 那 1 处 ldr 位移通配）
确认，可挡住「定位到错误函数」。B、C 各有自己的指纹。
⇒ 建议 P2 守卫加一条：**定位结果必须通过对应形状的整函数指纹校验**。

# 追加 · 用 Ghidra 逆向 M6 目标函数并跨版本对比（2026-09-18 晚）

## 做了什么
把 `FS_unc.kip1` 拼成 AArch64 ELF 喂给 **Ghidra 12.1.2 无头**反编译，拿到 8 个代表性版本的
C 伪代码，做 5 层归一化对比。**用一条完全独立的路径复现了指令级的「3 形状」结论**。
报告 → `M6_Ghidra反编译报告.md`；主报告新增 §10。

## 关键技术点

### 1. KIP1 → Ghidra（Ghidra 没有 KIP1 loader）
- 段布局（**48 个变体公式 100% 成立**）：文件 = `[0x100 KIP1 header][.text][.rodata][.rwdata]`，
  `0x100 + hdr[0x24](text_size) + hdr[0x34](rodata_size) + hdr[0x44](rwdata_size) == 文件大小`。
- ★ 坑：**文件偏移 ≠ 运行期偏移**。三段在文件里紧挨着，但运行期 rodata/rwdata 有页对齐
  （19.0.1/081b：text 数据 0x1CB0E4，rodata 运行期 0x1CC000，差 0xF1C）。必须逐段换算。
- 做法：自建极简 ELF（ET_EXEC / EM_AARCH64 / 3 个 PT_LOAD，权限 R+X / R / RW，
  vaddr = `0x7100000000 + 段相对地址`）。readelf 验证通过，Ghidra 正确识别。
- 收益：`.rwdata` 被正确映射 ⇒ `adrp`+`ldr` 引用的 fs 编码上下文槽解析成 `DAT_710024eb50`。

### 2. Ghidra headless 的两个坑
- **全程序分析要 90–120 s**，而本环境**后台任务 ~2 分钟就被回收** ⇒ 任务总跑一半死。
  改用 `-noanalysis` + 脚本里 `DisassembleCommand` 定向反汇编 + `createFunction` + `f.setBody()`
  ⇒ **秒级**。（注意：这样 meta 里的 `stack_frame`/`callees` 不可靠，栈帧要从 asm 的 `sub sp` 读。）
- **`<projDir>` 必须预先存在**，否则 `Directory not found` 并 `pause`；
  另：`cmd /c "... < NUL"` 会被 cmd 解析报「此时不应有 <」，用 PowerShell 原生 `*> $log` 即可。

### 3. 函数语义（C 代码确认）
`p11–p26` 所在函数 = **编码域感知的宽字符路径通配符匹配**：
```
match(c1, StringDesc* s1, c2, StringDesc* s2)
  c2=='?' → c1 必须非 0；c2==0 → 双双结束才算匹配；
  c2=='*' → 跳过连续 * / ?，到串尾则成功，否则对 s2 每个位置递归回溯
  next_char: encode_type==1 → u16 / pos+=2 / 边界 <0x20B
             else            → u8  / pos+=1 / 边界 <0xB，多字节前导则 CONCAT11(b0,b1)
  两次大小写折叠：'a'..'z' → -0x20，再 'A'..'Z' → -0x20
```
第一行 `ctx = *(Ctx**)0x710024EB50`，`(*(ctx+0x30))(byte,1)` = 多字节判定回调
⇒ 与 §9 发现的「同一 fs 编码上下文槽」吻合。

### 4. 五层归一化的分组演化（8 个版本）
| 层 | 内容 | 组数 |
|---|---|---|
| N0 raw | 原样 | 8 |
| N1 sym | 函数名/标签/代码地址符号化 | 5 |
| N2 ctx | 再把 fs 编码槽归一 | 5 |
| N3 var | 再归一 Ghidra 局部变量名 | **3** |
| N4 skeleton | 只留控制流与运算符 | **3** |
| N5 set | N4 + 抹掉跳转标签编号 | **3** |

**N3 起稳定 3 组 = 指令级 3 形状**：{16.1.0} / {17.0.0, 18.x, 19.0.1, 20.x} / {21.x, 22.x}。
**14 个非地址立即数（`0xb 0xc 0x10 0x19 0x20 0x2a 0x30 0x3f 0x61 0xbf 0x20a 0x20b 0xffe0 0xffff`）
在 8 个版本里完全相同。**

### 5. 差异性质（人工逐条核对）
- **A ↔ A**：数据槽地址 + 栈槽命名 + 指针/数组书写形式。
- **A ↔ C(16.1.0)**：骨架层只差 **5 行**（`A[B]` ↔ `*(A+B)`）；栈帧 `#0x90` ↔ `#0x80`。
- **A ↔ B(21/22)**：N3 后 38 行，全部是
  ① **基本块排列顺序互换**（A 先 UTF-16 块后 OEM 块，B 反之）；
  ② **等价指令选择**（`add #0xffe0` ↔ `sub #0x20`；`orr lsl#8` ↔ `bfi #8,#8`）。
  ⇒ §9 说「B vs A 不是寄存器重命名」，这里给出正面解释：**是代码布局 + 指令选择**。

## 归一化自身踩的坑（写脚本时）
- 地址是 **10 位**十六进制（`FUN_71000e32b0`），按 12 位写正则会全部漏掉。
- 两种分析模式下同一全局引用分别显示成 `DAT_7100240b50` 与 `lRam0000007100240b50`；
  函数名分别是 `FUN_...` 与自建的 `M6_target`/`func_ADDR` ⇒ 归一化必须同时认这些形态。
- `uStack_88` / `lStack_70` 这类栈槽命名依赖前缀，正则漏 `lStack` 会让 21/22 误分两组。
- 切片后缀 `VAR._0_4_` 里的数字会被 token 化 ⇒ 骨架层先做变量归一、再去切片后缀。
- **混用两种分析模式产生纯噪声**（类型推断不同 → `byte *VAR` vs `long VAR`）⇒ 必须统一模式重跑。
