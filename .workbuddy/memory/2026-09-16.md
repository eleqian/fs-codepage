### 结论
1. **RetroArch = 核心与主程序版本不配套（确凿）**：`switch/retroarch_switch.nro` 是 2026-01-13，
   `retroarch/cores/` 51 个核心是 2026-02-10/11（另有 2 个 2025-11-16），
   `retroarch/info/` 只有 6 个且是 1/13 的。`retroarch.cfg` 的
   `core_updater_buildbot_cores_url` 指向 nightly latest —— 用内置 updater 更新了核心
   但没更新主 nro，Switch 版核心与主程序必须同一构建，故加载核心必挂。
2. **崩溃点不是第一现场**：7 份崩溃（2026-09-16 00:02–00:06，program id
   01524d47b3c10000=RetroArch / 05446530aca7e000=PPSSPP）全是 `Data Abort`、
   `X0=X20=0xFFFFFFFxxxxxxxxx`、`X1 = PC-0x14`。反汇编四个无关 nro（PPSSPP_GL、
   retroarch_switch、appstore、NX-Shell）在同一模式处得到**逐字节相同**的代码
   = libstdc++ `__cxa_finalize` 静态对象析构（遍历 27 项 bitmask 调 dtor）。
   即程序已走 exit，清理时二次崩溃。
3. **与我们的 fs 编码补丁无关**：4 月 19/21 日已有同址同型崩溃
   （`PPSSPPSDL + 0xe1c6d0`，与 9/16 完全一致，且 PPSSPP_GL.nro 是同一文件），
   而 fs_codepage 补丁 9/15 才启用。
4. PPSSPP 嫌疑（中，待上机验证）：`switch/ppsspp` 与 `switch/PPSSPP` 两个仅大小写
   不同的目录并存（各带 assets/config/PPSSPP_GL.nro），Switch fs 大小写不敏感 → 未定义行为；
   且全盘搜不到 `ppsspp.ini`，config 是 2023-12-24 的空壳。nro 与 assets 同为 2026-02-12，二者配套。
5. SD 卡根目录有 `FOUND.000`（2026-02-15）= FAT 曾损坏，列为背景风险。
   SaltyNX 在跑但 `/SaltySD` 无 plugins 目录，暂不列嫌疑。

  变通：把结果 `Out-File` 到文件再用 Read/Python 读。

  长扫描要一次抓完，别依赖二次访问。

  **取证结论若建立在"没找到"上，必须先确认卡在线**（`os.path.exists('F:/')`）。

  正则类一次性脚本要写成 .py 文件再跑；`python xxx.py | head` 会因 SIGPIPE 杀掉脚本
  导致尾部落盘不执行，应 `> file` 再读。
