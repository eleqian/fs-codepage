# 2026-09-20 · fs 整函数替换功能合理性评估（Ghidra 复核）

产物：`fs_encode_fix/re_整函数替换功能评估.md`

## 复核方法
Ghidra MCP（工程 `FS_1`，程序 `/19.exfat.FS.kip1`，base 0x7100000000）反编译原版 + 全部调用者，
对照 `sysmod/src/fs_codepage.cpp` 的 7 个替换体；尺寸用 `check_patch_sizes.py` 重跑实测。

## 关键新事实（都能复用）
- ctx 表 `PFCODE_CODE_PAGE_CONTEXT @0x7100FCFC38`（.bss，运行期填充）槽位实测：
  `+0x18` OEM2Unicode=0xFEAC0(p03) / `+0x20` Unicode2OEM=0xFEC30(p02) /
  `+0x28` OEMCharWidth=0xFEE00 / `+0x30` isOEMMBchar=0xFEE40(p04) /
  `+0x38` UnicodeCharWidth=0xFEE90(恒 2) / `+0x40` isUnicodeMBchar=0xFEEA0(恒 false) /
  `+0x48` = 0x7100FCFC80 特殊映射标志。原函数从 0x710024EB50 取 ctx 指针。
- **返回值契约**：`ConvertWidth(oemBytes, uniBytes) = oem<<16 | uni`（0xF7CE0/0xF7CF0）。
  `uniWidth` 是 **UTF-16 字节数** ⇒ 返回 `(4<<16)|4` 就能写代理对（4 字节 UTF-8 支持是可行的）。
- **未替换的 3 个原语是正确决策**：OEMCharWidth 直接调 +0x18（宽度自动跟随）；
  UnicodeCharWidth/`isUnicodeMBchar` 是常量。无需新增条目。
- p06 规则语义确认：`FAT_GetNextPathComponent` 的 `add #1` 之后紧跟一次 `pcVar5+1`
  ⇒ w0 = "额外字节数"是对的（后一处补上那个 1）。
- `FAT_GetNextChar` / `WideChar_Compare` 各只有 2 个调用者；`StringDesc_ToUpper` 只有 1 个。
  替换面闭合。

## 发现（写入报告，待做）
1. **P0 `patch_str_unicode2oem` 界不成立**：`limit=out+512` + 逐字符判界、逐字节写（最多 3）
   ⇒ 写满时 `*out='\0'` 可落在下标 513/514。`lname[513]` 越界 1–2 B（写进 `unicode_name`）；
   `FAT_MakeShortName` 的 **512 B 栈缓冲**越界 1–3 B（落进紧随的 4 B `local_74`，侥幸不致命）。
   修法：`while (*in && out + 3 <= limit)`（特殊分支 `+1`）。余量 64 B 够。
2. **P0 p27 stage 偏晚**：p27（把 OEMCharWidth 宽度钳到 2，防 `FAT_MakeShortName`
   `subs w23,w23,#2` 死循环）是 stage 3，而 p02/p03/p04 是 stage 0 ⇒
   `stage ∈ {1,2,3}` 时转换器已换但钳制未打 ⇒ FAT32 建 CJK 名死循环。建议 p27 → stage 0。
3. **P1 `+0xffe0` 影响面已量化**：Ghidra 证实该路径 OEM 名字上界 `pos < 0xB`（11 B = 8.3 短名），
   短名被大写化 ⇒ 实际几乎不可达。保留可接受，但注释"必须复刻"定性过头。
4. **P1 4 字节 UTF-8 → `'_'`**：接口支持代理对（见上），属产品取舍；
   现状会让不同非 BMP 名字折叠同名（比越界更日常）。
5. **P2 p04 零余量 0x50/0x50，守卫仍无 `ZERO SLACK` 告警**（O4 未做）。
6. **P2 `patch_utf16_to_utf8` 注释与实现不符**：3 字节分支第 3 字节是续字节非 NUL；
   1 字节分支写 `[2]='\0'` 却不写 `[1]`（原版写 `[1]`）。现调用点安全，属潜在风险。

## 建议（回答"是否要与旧指令级补丁一致"）
把差分口径从「orig+旧补丁 vs 替换体（比指令产物）」改成**行为级三者比较 + 差异白名单**
（比 返回值/输出缓冲/步进量），结构性缺陷（p28 越界）才会在差分里现形，
"顺手修 bug"也才可验证。

## 1. 结构体合并 → `FsObj24`
- 事实：`StringDesc`（encode_type）、字符迭代器（cw）、模式流（cur/end/mode）三个 fs 对象**内存布局完全相同**

# 2026-09-20（续4）· 结构体再简化：`FsObj24`（union）→ 单一 `StringDesc`

用户追问「FsObj24 能否直接用 StringDesc 不做 union」，评估后决定**采纳**（去掉 union）。

## 关键认识
三处 `+0x10` 本就是**同一个字段**（「编码/宽度」选择子）：StringDesc 的 `encode_type`（ENCODE_OEM=1）、
字符迭代器的 `cw`（==1 单字节）、模式流的 `mode` 低 32 位（==1 单字节）—— 语义一致，**不需要各挂别名**。
且 `ptr_right`/`mode` 在代码里**从未被解引用**（只在 static_assert/注释）。故 union 是多余的。

## 改法（`sysmod/src/fs_codepage.cpp`）
- 定义 `typedef struct { void *ptr_left; void *ptr_right; u32 encode_type; u32 reserved; } StringDesc;`
  （`+0x14 reserved` 显式声明 ⇒ 恰 24 B **无尾部填充**，`*ps` 整对象拷贝字节数确定，不依赖编译器对 padding 的处理）。
- `static_assert` 锁 `sizeof==24` + 四偏移；删除原三组 union 别名与 4 条旧断言。
- 字段访问改写：`patch_fat_getnextchar` 里 `d->cur`→`(u64)d->ptr_left`（写回 `(void*)(cur+..)`）、
  `d->end`→`(u64)d->ptr_right`、`d->cw`→`d->encode_type`；`patch_stringdesc_toupper` 不变；
  `patch_widechar_compare` 只把 `FsObj24*`→`StringDesc*`、`ps2` 类型跟着换。`FsNextChar` typedef 同。
- 注释同步：M6 布局块、fat 对象注释、`StringDesc` 定义块首。

## 验证
- `make` exit 0：`all 7 replacement functions and 15+16 fs patch entries verified`，0 ERROR，无 ZERO SLACK。
- ★ **7 个替换函数字节尺寸逐位不变**（`0x308`/776、`0x1E8`/488、`0x94`/148、`0xEC`/236、`0x8C`/140、
  `0x48`/72、`0xEC`/236）⇒ 证明 union→单体 是**零代码生成差异**的纯源码整理。
- `sysmod/build/sys-patch.map` 里 `FsObj24` 符号数 = 0（已重编译）。

## 改法（`sysmod/src/fs_codepage.cpp`）
- 文件顶新增 **§0 具名常量块**（全 `constexpr`/`#define`，展开后与原字面量逐位相同，**不改代码生成**）：
  编码选择子（`ENCODE_OEM`/`NAME_ENC_UTF16`/`FS_ENC_OEM2UNI`/`FS_ENC_UNI2OEM`）、ctx 槽位

  `_OEM=0xB`）、24 位比较位移（`NAME_BYTE1_SHIFT=8`/`BYTE2_SHIFT=16`）、哨兵 + `FS_ASM_STR`。

## ★ 关键坑：`.inst` 汇编字符串里不能写 C++ 宏名
`".inst FS_CTX_SENTINEL_A"` 会编译失败（`constant expression required`）—— **C++ 字符串字面量不被预处理宏展开**，
汇编器看到的是字面文字 `FS_CTX_SENTINEL_A`。修法：`#define FS_ASM_STR_(x) #x` + `#define FS_ASM_STR(x) FS_ASM_STR_(x)`，
写成 `".inst " FS_ASM_STR(FS_CTX_SENTINEL_A) "\n\t"`（先字符串化再拼接）。
