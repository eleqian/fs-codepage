### 第二十轮（分析）：CP936（GBK）替换方案评估 + 与 UTF-8 方案对比

- 产出 `fs_encode_fix/cp936_vs_utf8.md`。**结论：CP936 方案不成立，UTF-8 路线维持主线**。结构性优势真实（双字节域 ⇒ H1/R1/R2/R3/R7 消失、6 处步进免修），但被两个硬伤抵消：①客户端（libnx/nn::fs IPC）路径域是 UTF-8，OEM 域换 GBK 后打开/显示双向在 API 边界断裂，必须新增 StringDesc_SetPtr + DirectoryEntry 输出 2 个未逆向的边界转换点；②转换必须查表。
- **CP932 实现结构定案**（Ghidra 反编译）：单一共享表 `u16[0x2d][0xbd]`=8505 项=0x4272 字节 @0x71001db814，OEM2Unicode/Unicode2OEM 唯一数据依赖、单表双向复用（反向=线性扫描，无独立反查表）。行=lead 五段压缩（0x81-84:−0x81/0x87-9F:−0x83/0xE0-EA:−0xC3/0xED-EE:−0xC5/0xFA-FC:−0xD0），列=trail−0x40；空位=0→输出 '_'。PFCODE_CP932_Init@0x71000d5150 注册 6 回调至 PFCODE_CODE_PAGE_CONTEXT@0x7100fcfc38 +0x18..+0x40（.bss，sysmod 无法静态 patch，改指针通道不可行）。
- 表空间测算：GB2312 87×94=0x3FE4 **可就地覆盖**（仅 6763 汉字）；全 GBK 126×190=0xBB08 需重定位（表后 0x71001dfa86 起已是其他数据）。GBK 尾字节含 0x5C，继承 CP932 同类路径分隔符碰撞；UTF-8 续字节 0x80-0xBF 免疫。

### 第二十二轮（同日续）：废除 PATCH_SZ_* 宏，运行时自动取补丁尺寸（commit b63fd92）

- 实现：每个 patch_* 函数加 `__attribute__((used, section(".text.<函数名>")))`，函数体后放 `__asm__` 结束标签 `<函数名>_end`，`patch_code_size()`（模板，因 C++ 函数指针不能隐式转 void*）运行时算 `end − func`。调用点 `(int)patch_code_size(f, f##_end)`。
- **关键坑 1**：GCC 把顶层 asm 全部提前发射、函数体延迟发射 → 标签落在函数前、尺寸恒 0。解法 = sysmod CXXFLAGS 加 `-fno-toplevel-reorder`（标签才落到函数体后）；改 CXXFLAGS 不会触发重编，必须 touch 源文件。
- **关键坑 2**：sysmod/Makefile 是外层/内层双 pass 结构（`ifeq ($(BUILD),$(notdir $(CURDIR)))`），check 目标若定义在拆分之前会成为内层 make 的默认目标，静默跳过全部编译。守卫目标必须放外层段尾部（`all`/`dist` 之后）。
- 校验脚本改为：标签 delta == ELF st_size（防标签错位，即上述坑 1 的失败模式）+ ≤ 空洞。`update-patch-sizes` 目标已删（无宏可回写）。实测尺寸 0xEC/0x7C/0x44/0x110/0x94（toupper 比旧宏 0x98 小 4 字节，证明手工维护确有漂移）。
- 调试技巧：`aarch64-none-elf-g++ -S` 探针需 Windows 风格 `-IC:/devkitPro/...` 与全套 -D 宏；沙箱内 Windows 原生工具读不到 Git Bash 的 /tmp，临时文件放仓库内。

## 2026-09-14 大目录枚举「子目录识别为文件」根因（Ghidra）
- 新结论文档：`fs_encode_fix/re_bigdir_dir_as_file.md`。与 codepage 补丁无关。
- 根因：fs 的条目复用/去重身份键 = (pDrvObj, dirCluster, wEntryOffset)，而 wEntryOffset 只是扇区内偏移 (index & mask)<<5，同簇内索引差 16（512B 扇区）整数倍的项身份碰撞。
- 证据函数：fat_read_next_directory_entry@0x71000f89a0（wEntryOffset 计算）、fs_iterate_directory_entries@0x7100106de0（枚举复用，目录+无打开目录对象时走文件池查找→目录按已打开文件上报）、fat_find_file_context_by_id@0x71000ff540（弱键，不比 firstCluster/dwEntryIndex）、fs_stat_by_path@0x7100107190 与 fs_open_entry_worker@0x71001094e0（同款复制粘贴）、fat_find_or_alloc_dir_object@0x7100109e40（目录池去重同弱键）。
- 可观察特征：被误报项的名字应与某个（打开中）文件重名、真子目录消失；关掉持有句柄的软件后复现消失。

## 2026-09-14 第五轮（用户问：内部文件能否污染子目录自身）
- 否定（机制级）：弱键 dirCluster@0x244 = 父目录簇号；GBA 内部文件的 dirCluster=GBA 自身簇 ≠ /roms 簇，永不匹配。内部文件只能污染子目录内容列表，不可能影响子目录在父目录里的条目；FAT/exFAT 也无「改写父目录中子目录条目 attr」的写路径。
- 分支条件修正：文件条目→有打开文件即文件池复用；目录条目→仅 drvObj+0x9c（打开目录计数）==0 才走文件池复用，有目录打开时扫目录池（命中=碰撞兄弟目录，type 仍 Directory，只串名不变形）。
- 推论：扫描时 app 持有 /roms 会话 → 0x9c>0 → 目录条目的文件池复用与 fs_stat_by_path 同守卫 → 假说 B 被压制，假说 A'（盘上隐藏同名 0 字节文件）权重上升。
- 新判别：Switch 上 GBA 出现两次（文件夹+0字节文件）→ A' 实锤；只出现一次 → A' 排除，转向 app 侧展示逻辑。
